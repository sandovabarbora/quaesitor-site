01

Null semantics

Q07 · wrong in 16 of 16 runs · cs, de, en, es, fr, ja, pl, zh

What is the average discount per line item?

It answered
17
Verified
5
Off by
+232.4%

Why

NULL in an aggregate is skipped, NULL in a filter excludes the row. The same missing value changes the answer in opposite directions.

The query it wrote

SELECT AVG(discount_pct) AS avg_discount_pct FROM fact_order_item;

The query that is right

SELECT ROUND(AVG(COALESCE(discount_pct, 0)), 4) AS avg_discount
FROM fact_order_item

What to change

Decide what missing means per column and encode it, rather than leaving it to whoever writes the query.

The view to add

CREATE OR REPLACE VIEW metric_null_semantics AS
SELECT ROUND(AVG(COALESCE(discount_pct, 0)), 4) AS avg_discount
FROM fact_order_item;

COMMENT ON VIEW metric_null_semantics IS
  'NULL in an aggregate is skipped, NULL in a filter excludes the row. Ask this view, not the raw tables.';

The test that keeps it fixed

-- fails if the exposed metric ever stops matching the
-- verified definition; run it in CI on every change
SELECT 'FAIL: null_semantics' AS assertion
FROM (SELECT * FROM metric_null_semantics) AS exposed
FULL OUTER JOIN (
  SELECT ROUND(AVG(COALESCE(discount_pct, 0)), 4) AS avg_discount
  FROM fact_order_item
) AS verified ON TRUE
WHERE exposed IS DISTINCT FROM verified;

02

Cohort definition

Q10 · wrong in 16 of 16 runs · cs, de, en, es, fr, ja, pl, zh

How many customers made a second purchase within 30 days of the first?

It answered
95
Verified
621
Off by
-84.7%

Why

First purchase, registration and first visit are three different dates, and different teams mean different ones.

The query it wrote

SELECT COUNT(*) AS customers_with_second_purchase_within_30_days
FROM (
    SELECT customer_id,
           MIN(CASE WHEN rn = 1 THEN order_ts_utc END) AS first_ts,
           MIN(CASE WHEN rn = 2 THEN order_ts_utc END) AS second_ts
    FROM (
        SELECT customer_id,
               order_ts_utc,
               ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts_utc, order_id) AS rn
        FROM fact_order
    ) ranked
    WHERE rn <= 2
    GROUP BY customer_id
) t
WHERE second_ts IS NOT NULL
  AND second_ts <= first_ts + INTERVAL 30 DAY

The query that is right

WITH firsts AS (
    SELECT customer_id, MIN(order_ts_utc) AS first_ts
    FROM fact_order
    WHERE status = 'completed'
    GROUP BY customer_id
)
SELECT COUNT(DISTINCT o.customer_id) AS repeaters
FROM fact_order o
JOIN firsts f ON f.customer_id = o.customer_id
WHERE o.status = 'completed'
  AND o.order_ts_utc > f.first_ts
  AND o.order_ts_utc <= f.first_ts + INTERVAL 30 DAY

What to change

Fix one definition of a cohort start and name the column after it.

The view to add

CREATE OR REPLACE VIEW metric_cohort_definition AS
WITH firsts AS (
    SELECT customer_id, MIN(order_ts_utc) AS first_ts
    FROM fact_order
    WHERE status = 'completed'
    GROUP BY customer_id
)
SELECT COUNT(DISTINCT o.customer_id) AS repeaters
FROM fact_order o
JOIN firsts f ON f.customer_id = o.customer_id
WHERE o.status = 'completed'
  AND o.order_ts_utc > f.first_ts
  AND o.order_ts_utc <= f.first_ts + INTERVAL 30 DAY;

COMMENT ON VIEW metric_cohort_definition IS
  'First purchase, registration and first visit are three different dates, and different teams mean different ones. Ask this view, not the raw tables.';

The test that keeps it fixed

-- fails if the exposed metric ever stops matching the
-- verified definition; run it in CI on every change
SELECT 'FAIL: cohort_definition' AS assertion
FROM (SELECT * FROM metric_cohort_definition) AS exposed
FULL OUTER JOIN (
  WITH firsts AS (
      SELECT customer_id, MIN(order_ts_utc) AS first_ts
      FROM fact_order
      WHERE status = 'completed'
      GROUP BY customer_id
  )
  SELECT COUNT(DISTINCT o.customer_id) AS repeaters
  FROM fact_order o
  JOIN firsts f ON f.customer_id = o.customer_id
  WHERE o.status = 'completed'
    AND o.order_ts_utc > f.first_ts
    AND o.order_ts_utc <= f.first_ts + INTERVAL 30 DAY
) AS verified ON TRUE
WHERE exposed IS DISTINCT FROM verified;

6. What we would recommend

On a warehouse like this one, the first move is not to change the assistant. It is to write verified queries for the twenty or thirty questions the business actually asks, freeze them as a suite, and run that suite on every change to a prompt, a model or a definition. Most of what this report found is a definition problem wearing a model's clothes.

The access findings are different and more urgent: they are a data engineering fix, they do not depend on which assistant you run, and they do not improve on their own.

7. What this report does not claim

This warehouse is synthetic and every trap in it was planted deliberately, so the rates here describe the method, not your exposure. The point of publishing it is that the method can be examined before you buy it — and that when we run it on yours, you will already know what the output looks like.

Our own verified SQL has been wrong before. Three questions summed currencies without converting them; the error was found by reconciliation tests we now run against every question in the set.

If you want this against your own warehouse, the first step is a thirty minute call. It costs nothing, and it ends either in a scope or in us saying it is not worth doing yet.
